## 三日與月統計的定義

- 以台北的日曆日計算；包含選定當日及前兩日，不是 72 小時，也不自行跳過週末。
- 當日有明確的「已叫貨」或「今日不叫貨」時優先採用；其餘客戶已追蹤至少三日、且三日內沒有已叫貨，才顯示「三日未叫貨」。因此當日四類相加恰等於當日納入的客戶數。
- 三日狀態是推導結果，不把 `overdue` 寫進舊 `orders.status`，也不能手動指定；資料庫仍相容 `pending / ordered / off`。
- 新增客戶從 `tracking_since` 開始，預設未叫貨。舊客戶缺少起日，依最早保存的叫貨日期補值；沒有紀錄者從本次本機補值／資料庫遷移日開始，不虛構前三日歷史。
- 月報排除未來日期及客戶開始追蹤之前的日期。「客戶日」表示一位客戶一天一筆，避免把整月累積誤標成當前客戶家數。總計客戶為目前啟用家數，日期明細則顯示該日已開始追蹤的家數。
- 系列可以重疊，不能把各系列的數字相加當作公司總計；客戶停用後不再列入此營運月報，這不是主檔歷史快照報表。
- 跨台北午夜時，仍停在當日時會切至新日；正在查看其他歷史日期時保留日期。沒有以每分鐘全表查詢來達成此功能。

## 正式 Supabase 更新

已有 v1.0 的專案，只需在備份後於 SQL Editor 執行 [02_dashboard.sql](../sql/02_dashboard.sql)。新專案先執行 `01_workspace.sql`，再執行 `02_dashboard.sql`。新版需用新增 RPC 取得三日與月統計；只更新 GitHub 的前端程式不會替資料庫執行 SQL。

`02` 增加小型摘要 RPC、已叫貨查詢索引、追蹤起日 trigger 及可重跑的補值；保留未知欄位，補值會增加 revision 並發送通知。沒有 DROP TABLE 或直接改寫既有 status。無正式管理員資料庫連線，因此本次不宣稱已部署到使用者 Supabase。

本機模式不需 SQL，即可使用全部本次介面功能。若雲端未部署新版 SQL，畫面會顯示統計載入失敗；不會把未知三日狀態假稱已核對。刪除自訂系列仍遵守既有管理員權限。

## 更新流量

月報首次開啟／切換月份才取整月聚合結果，客戶摘要每個營業日只用一個狀態字元（最多 31 個），不下載原始歷史 JSON。之後一般單一客戶異動只補查該客戶的月摘要，並在前端扣除舊值、加上新值，連帶更新每日與系列數字。當日三日判斷同樣只補查受影響客戶。主檔／系列改變、跨日或大量批次變更時才重新取得完整聚合結果。既有 30 秒水位檢查維持小型請求。

上述設計有純函式、PostgreSQL 相容資料庫與模擬雲端介面的測試；尚未在正式 Supabase 帳戶實測 Realtime 延遲或 Egress。
